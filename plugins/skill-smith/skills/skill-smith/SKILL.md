# Skill-smith — инженерия конфигурации Claude Code

Конфигурация Claude Code — это код, который исполняет харнесс. Он молча деградирует:
битый YAML не падает с ошибкой, а тихо загружает скил с пустыми метаданными; лишнее поле
игнорируется; слишком общее описание превращает скил в шум в каждой сессии.
Поэтому здесь тот же цикл, что и в коде: сверился → спроектировал → написал → провалидировал → проверил.

## Железное правило

**Frontmatter, пути и синтаксис — только из первоисточника, никогда по памяти.**
Поверхность конфигурации Claude Code меняется каждые пару недель: поля `background`, `paths`,
`when_to_use`, `arguments`, `${CLAUDE_PROJECT_DIR}`, `skillOverrides` появились с привязкой к
конкретным версиям. Знание из головы устарело по определению.

Не работает как оправдание: «поле очевидное», «это же просто `name` и `description`»,
«правка на одну строку», «я это делал неделю назад».

## Шаг 0 — сверка с документацией (обязательно, до первой строки)

Официальные доки отдаются в markdown, если дописать `.md` к пути:

| Тема | URL |
| --- | --- |
| Скилы и слэш-команды | `https://code.claude.com/docs/en/skills.md` |
| Настройки (все ключи) | `https://code.claude.com/docs/en/settings.md` |
| Хуки и события | `https://code.claude.com/docs/en/hooks.md` |
| Субагенты | `https://code.claude.com/docs/en/sub-agents.md` |
| Плагины и маркетплейсы | `https://code.claude.com/docs/en/plugins-reference.md` |
| Права и разрешения | `https://code.claude.com/docs/en/permissions.md` |
| CLAUDE.md и память | `https://code.claude.com/docs/en/memory.md` |
| Переменные окружения | `https://code.claude.com/docs/en/env-vars.md` |
| Полный индекс страниц | `https://code.claude.com/docs/llms.txt` |
| Портируемая спека Agent Skills | `https://agentskills.io/specification` |

Правила сверки:
- Тянем **страницу под задачу**, а не общий обзор. Сомнение в поле — открываем таблицу полей.
- Если docs.claude.com отдаёт 301 на code.claude.com — идём по редиректу, это актуальный хост.
- Дока большая: сначала оглавление (`grep '^#'` по скачанному), потом нужный раздел.
- Локальный кэш контракта: [references/frontmatter.md](references/frontmatter.md) — таблица полей,
  подстановки, инъекции, лимиты, приоритеты уровней, портируемость.
- **Когда живой фетч не нужен.** В шапке каждого справочника — дата сверки и версия Claude Code.
  Если дата сегодняшняя и версия совпадает с `claude --version` — работаем по кэшу, не тянем доку.
  Тянем живьём, если: дата старше сегодняшней, версия разошлась, речь о фиче, которой в кэше нет,
  или поведение на практике разошлось с написанным. После живого фетча — обнови кэш и дату в шапке.
- Не гадаем и по версиям: `claude --version`, поведение поля часто привязано к версии.

## Шаг 1 — выбрать механизм

Половина плохих скилов — это задача не для скила. Выбираем по природе требования:

| Что нужно | Механизм | Почему |
| --- | --- | --- |
| Знание/конвенции, применяемые по ситуации | скил (тело грузится по требованию) | не жрёт контекст, пока не нужен |
| Факт, который нужен **всегда** | `CLAUDE.md` | скил может не сработать |
| Многошаговая процедура по команде человека | скил + `disable-model-invocation: true` | «/deploy» решает человек, не модель |
| Изолированное исследование с большим выхлопом | скил + `context: fork` (+ `agent: Explore`) | мусор не попадает в основной контекст |
| Переиспользуемая роль с своим системным промптом | субагент в `.claude/agents/` | у скила нет своего системного промпта |
| Гарантия «всегда при X» (форматирование, запреты) | хук | скил — рекомендация, хук — исполнение харнессом |
| Разрешения, env, модель, статуслайн | `settings.json` | не место для скила |
| Раздача набора скилов+хуков+агентов другим | плагин + маркетплейс | версионируется и обновляется |
| Доступ к внешней системе | MCP-сервер | скил не даёт новых инструментов |

Правило разделения: **скил рекомендует, хук обеспечивает.** Если поведение должно выполняться
детерминированно и без участия модели — это хук, сколько бы капслока ни было в скиле.
Подробнее по каждому механизму и его файловому формату: [references/mechanisms.md](references/mechanisms.md).

## Шаг 2 — контракт скила (до написания тела)

Зафиксируй пять решений и только потом пиши:

1. **Уровень.** Проект (`.claude/skills/`, в git, работает у всех) / личный (`~/.claude/skills/`,
   не виден в cloud и routines) / плагин (раздача). По умолчанию для работы над проектом — проектный.
2. **Имя команды = имя каталога.** Для personal/project скилов поле `name` — только ярлык в листинге.
   Каталог именуем глаголом в kebab-case: `review-pr`, `deploy-staging`, а не `pr_helper`.
3. **Кто вызывает.** Граница проходит по тому, **меняет ли скил состояние**:
   - меняет — правит файлы проекта, ставит зависимости, запускает миграции, коммитит, деплоит,
     отправляет наружу → `disable-model-invocation: true`, **всегда**.
     Локальная правка файлов — тоже побочный эффект: «это же откатывается через git» не аргумент,
     потому что скил может сработать в репозитории с грязным деревом или вообще без git.
   - только читает и советует (конвенции, справка, разбор) → оставляем модели.
   - фоновое знание, которое человеку нечего вызывать руками → `user-invocable: false`.
4. **Description = только условия срабатывания.** Не пересказ процесса.
   Пересказ процесса в описании модель принимает за инструкцию и не читает тело.
   - плохо: `Проверяет диффы, пишет отчёт и постит комментарии в PR`
   - хорошо: `Используй когда нужно отревьюить изменения перед мерджем или разобрать замечания в PR`
   Пиши **слегка напористо**: модель скорее недотриггерит, чем перетриггерит, — формулируй
   «используй, когда просят X, даже если слово X не прозвучало». Лимит `description` +
   `when_to_use` — 1536 символов (для переносимости в claude.ai/API — 1024 на `description`),
   ключевой кейс первым.
5. **Что даём в frontmatter.** Каждое поле — под конкретную нужду:
   аргументы → `argument-hint` (значение с `[...]` **в кавычках**) + `arguments`;
   свой скрипт без запроса прав → `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/x.sh *)`;
   тяжёлая задача в изоляции → `context: fork` + `agent` + при нужде `background: false`;
   привязка к файлам → `paths`. Всё остальное не добавляем.

## Шаг 3 — тело скила

Тело входит в контекст **одним сообщением и остаётся до конца сессии**, файл повторно не читается.
Значит, это стоячие инструкции, а не рассказ и не одноразовый чек-лист.

Тело состоит из следующих частей, в этом порядке:

1. Одна строка: что это и какой принцип за этим стоит.
2. Жёсткие правила и запреты — императивами, в настоящем времени, адресно.
3. Шаги процедуры — нумерованный список, каждый шаг проверяем по факту («прогони X, ожидай Y»).
4. Таблица быстрой справки — то, к чему возвращаются глазами.
5. Типичные ошибки и как их чинить.
6. Ссылки на вспомогательные файлы с указанием, что внутри и когда открывать.

Что попадает в тело, а что нет:

- Проверка каждой строки: **«модель ошибётся без этой инструкции?»** Нет — вычёркиваем.
  Скил добавляет то, чего у модели нет, а не пересказывает общеизвестное.
- **Точность по хрупкости**: там, где валидных путей несколько — объясняем принцип и почему;
  там, где операция хрупкая — точная последовательность («выполни ровно эту команду, флаги не меняй»).
- **Один дефолт вместо меню.** Не список равноправных вариантов, а решение по умолчанию
  плюс короткая оговорка, когда от него отступать.
- **Грабли — в самом SKILL.md**, не в справочнике: модель не откроет файл, если не распознает,
  что наступила на них.
- Императив в настоящем времени. Капслочные ALWAYS/NEVER и жёсткие ритуалы — жёлтый флаг;
  объяснённое «почему» держится лучше, чем крик.
- **Запрет формулируй по операциям, а не по инструменту.** «Не трогай git» отрезает и `git status`,
  без которого скил не соберёт область правок. Правильно: «не делай `git add`, `git commit`,
  `git push`; читать `status`, `diff`, `log` можно».
- Скрипт вместо инструкции, если модель раз за разом переизобретает одну и ту же логику.

Держи `SKILL.md` в пределах ~500 строк (и ~5000 токенов); тяжёлый справочник — в отдельный файл рядом,
на который тело ссылается относительной ссылкой (`[frontmatter](references/frontmatter.md)`).
Скрипты — в `scripts/`, путь к ним пиши через `${CLAUDE_SKILL_DIR}`, иначе они не найдутся
при другом рабочем каталоге.

### Форма инструкции — по типу провала

Сначала посмотри в базлайне, **как именно** модель провалилась, и только потом выбирай форму.
Форма, которая бронирует один тип провала, на другом измеримо вредит.

| Провал в базлайне | Форма | Не работает |
| --- | --- | --- |
| знает правило и нарушает под давлением | запрет + дословная таблица «Отмазка → Реальность» + красные флаги | «желательно», «по возможности» |
| слушается, но вывод не той формы (раздут, вердикт утоплен) | рецепт: из каких частей и в каком порядке состоит вывод | список запретов — с ними торгуются |
| теряет обязательный элемент в том, что и так производит | обязательный слот в шаблоне, который она заполняет | напоминание прозой рядом с шаблоном |
| поведение должно зависеть от условия | условие на наблюдаемом признаке («если есть `spec.md` — …») | правило плюс оговорки-исключения |

Поверх любой выбранной формы:

- **Никаких оговорок «если это важно».** Одна такая приписка переводит работающий рецепт
  из стабильного в шумный. Настоящее исключение — отдельным условием на наблюдаемом признаке.
- **Исключающая клауза не скоупится.** «Ограничение не касается блоков кода» всё равно давит
  блоки кода. Часть вывода нужно вывести из-под правила — перестрой правило так, чтобы оно
  до неё не дотягивалось.

Разбор по каждому типу с примерами: [references/wording.md](references/wording.md).

### Добавление в готовый скил — только через второе мнение

Каждая дописанная строка живёт в контексте до конца сессии и конкурирует с уже написанными
правилами. Решение «нужен ли этот блок здесь» автор правки принять не может: контекст, в
котором ты только что нашёл красивый кусок, сам по себе аргумент за него.

Перед тем как дописать в существующий скил новый раздел, таблицу или правило — тем более
заимствованные из чужого скила:

1. Прогони `consult.sh challenge` со своим утверждением «это стоит добавить» — он локальный,
   бесплатный и часто снимает вопрос на месте.
2. Сомнение осталось — **обязательно** возьми внешнее мнение скилом плагина
   `second-opinion` (`/second-opinion:ask`).
   Вопрос ставится открыто и без твоего вывода: «вот что в скиле уже есть, вот что предлагается
   добавить, нужно или нет и почему» — не «подтверди, что стоит добавить».
3. Разбирай ответ по трём корзинам: сошлись / разошлись / заметила только она. Возражения
   «это дублирует уже имеющееся» и «это раздует тело без отдачи» — ровно то, ради чего спрашивали.

Шаг не требуется для опечаток, переформулировок без нового смысла и обновления дат сверки
в справочниках. Скил `second-opinion` не подключён в проекте — включи его или спроси другую
модель любым доступным каналом; отсутствие канала под рукой шаг не отменяет.

## Шаг 4 — валидация (никогда не пропускаем)

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/validate_skill.py <путь-к-скилу-или-каталогу>
python3 ${CLAUDE_SKILL_DIR}/scripts/validate_skill.py --portable <путь>    # если поедет в claude.ai/API
python3 ${CLAUDE_SKILL_DIR}/scripts/validate_skill.py --all .claude/skills # регресс по всему дереву
```

Ноль ошибок — обязательное условие сдачи. Предупреждения либо чиним, либо объясняем, почему они
неприменимы. Валидатор ловит ровно то, что харнесс проглатывает молча: битый YAML → скил
живёт с пустым описанием и просто перестаёт триггериться.

## Шаг 5 — проверка на свежем контексте

Отдельно проверяем **триггер** (вызывает ли модель сама на реальных формулировках) и
**качество** (меняется ли результат по сравнению с прогоном без скила). Оба — в чистой сессии
или сабагентом: контекст авторства маскирует дыры в тексте.
Методика, готовые уровни проверки и петля с плагином `skill-creator`:
[references/testing.md](references/testing.md).

Правило честности: «скил создан» — это не результат. Результат — «провалидирован, вызвался сам
на N формулировках, вывод отличается от базового вот этим».

## Шаг 6 — сдача

- Проектная конфигурация (`.claude/skills/`, `.claude/settings.json`, `.claude/agents/`) — под git.
- `.claude/settings.local.json` — личное, в `.gitignore`, туда же `skillOverrides` и локальные права.
- В ответе человеку: где лежит, как вызывается, что умеет, что проверено и что осталось непокрытым.

## Отмазки

| Отмазка | Реальность |
| --- | --- |
| «Я помню формат SKILL.md» | Поверхность меняется по версиям. Помнишь версию прошлого месяца. |
| «Это же просто name и description» | Именно так теряют `disable-model-invocation` у скила с побочками и `${CLAUDE_SKILL_DIR}` у скрипта. |
| «Правка на одну строку, сверяться незачем» | Одна незакавыченная строка с `[...]` кладёт весь frontmatter. |
| «Валидатор для чужих скилов» | Он ловит молчаливые отказы, а их не видно по глазам. |
| «Проверю, когда пользователь пожалуется» | Пользователь не пожалуется: скил не сработает, и он просто не узнает, что тот был. |
| «Скил напишу, тестировать долго» | Один прогон в свежем сабагенте — минута. Скил, который не триггерится, — ноль пользы навсегда. |
| «Опишу в description, что скил делает» | Описание процесса модель исполнит вместо чтения тела. |
| «Пусть модель сама решает, когда деплоить» | Побочные эффекты — только по команде человека. |
| «Блок хороший, чего тут обсуждать» | Хороший в чужом скиле ≠ нужный в этом. Второе мнение берут до правки, а не после. |
| «Спрошу — вторая модель всё равно согласится» | Согласие получает тот, кто просит подтверждения. Открытый вопрос без своего вывода приносит возражения. |

## Красные флаги — остановись

- Пишешь frontmatter, не открыв доку или `references/frontmatter.md` в этой сессии.
- В `allowed-tools`, `hooks` или `paths` появилось поле, точного имени которого ты не проверял.
- Скил делает коммит/деплой/отправку и при этом доступен модели.
- В description есть слова «затем», «после чего», «и потом» — это пересказ процесса.
- Ссылка на скрипт написана относительным путём без `${CLAUDE_SKILL_DIR}`.
- Говоришь «готово», не прогнав `validate_skill.py`.
- Тело перевалило за 500 строк и продолжает расти вместо выноса в `references/`.
- Дописываешь раздел в готовый скил, не спросив второе мнение «нужно или нет».
- Пишешь запрет там, где базлайн показывал не нарушение правила, а неверную форму вывода.
- Приписал к работающей формулировке оговорку «если это уместно».
