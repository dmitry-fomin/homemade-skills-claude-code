# Проверка скила: от «загрузился» до «работает»

То, что скил сработал, доказывает только что модель его нашла. Что он **что-то поменял** —
доказывает только сравнение с базлайном.

## Уровень 0 — статическая проверка (всегда, 2 секунды)

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/validate_skill.py <путь-к-скилу>
python3 ${CLAUDE_SKILL_DIR}/scripts/validate_skill.py --portable <путь>   # если поедет в claude.ai/API
python3 ${CLAUDE_SKILL_DIR}/scripts/validate_skill.py --all .claude/skills
```

Ловит: битый YAML (после которого скил грузится с пустыми метаданными и молча перестаёт
триггериться), неизвестные поля, превышение лимитов 1536/500, `agent`/`background` без
`context: fork`, взаимоисключающие флаги видимости, ссылки на несуществующие файлы,
инъекции `` !`cmd` `` без гранта Bash, объявленные и неиспользованные аргументы.

## Уровень 1 — загрузка в харнессе

1. `/skills` — скил в списке, в нужной группе (project / personal / plugin / claude.ai sync).
2. Спросить в сессии: «какие скилы доступны» — модель видит имя **и описание**.
3. `claude --debug` — если не видно, ищи ошибку парсинга frontmatter и предупреждение о
   переполнении бюджета листинга.
4. `/doctor` — стоимость листинга скилов и главные его пожиратели.

Правка `SKILL.md` подхватывается без рестарта; новый корневой каталог скилов — только с рестартом.

## Уровень 2 — триггер (вызывает ли модель сама)

Проверяется отдельно от качества, и правится при этом **только** `description`/`when_to_use`.
Рабочие числа из официальной методики (agentskills.io/skill-creation/optimizing-descriptions):

- **~20 запросов: 8–10 должны триггерить, 8–10 не должны.**
- Сильные негативы — это **близкие промахи**, соседние задачи, а не заведомо чужие темы.
- Каждый запрос гоняется **3 раза**; порог прохождения — доля срабатываний **выше 0.5**.
- Делим набор: **60% train / 40% held-out**; лучший вариант описания выбираем по held-out,
  иначе подгонимся под train.
- **Пяти итераций обычно достаточно.**
- Каждый прогон — в **свежем контексте** (сабагент или новая сессия): контекст авторства
  скила подсказывает модели ответ и маскирует дыры в описании.

Анти-правило: **не вставляй в описание конкретные слова из проваленного запроса** — это
переобучение, соседняя формулировка снова провалится. Обобщай намерение пользователя.

Полезно помнить про природу недотриггера: модель тянется к скилам за тем, чего не умеет сама.
Простой односложный запрос может не поднять скил, даже если описание идеально подходит.
Поэтому официальная рекомендация — **описание должно быть слегка «напористым»**:
формулировать не «этот скил делает X», а «используй, когда пользователь просит X, даже если
он не назвал X прямо». Ложные срабатывания лечим сужением условия или `disable-model-invocation: true`.

## Уровень 3 — качество вывода (baseline A/B)

### Фаза 1 — микротест формулировки (до дорогих кейсов)

Полный A/B меряет вывод скила целиком и стоит дорого за итерацию. Прежде чем гонять кейсы,
проверь **сами слова** новой инструкции:

1. Один свежий контекст на прогон — сырой вызов API или одноразовый сабагент.
   Системный промпт — **то окружение, в котором инструкция будет жить** (весь скил целиком),
   а не инструкция в вакууме: в вакууме держится почти любая формулировка.
   Пользовательское сообщение — задача, которая провоцирует именно этот провал.
2. **Контроль без инструкции обязателен.** Контроль не воспроизвёл провал — инструкцию
   не пишем, а уже написанную удаляем: чинить нечего, а лишние строки конкурируют
   с остальными правилами скила и портят то, что работало.
3. **5+ повторов на вариант.** Один прогон не значит ничего.
4. **Каждое размеченное совпадение читаем глазами.** Считать grep'ом можно, верить нельзя:
   эхо шаблона и процитированный контрпример («не делаю X, потому что…») выглядят как
   попадание и завышают разом и провал, и успех.
5. **Разброс — это метрика.** Инструкция легла — повторы сходятся к одной форме. Пять разных
   трактовок в пяти прогонах означают, что формулировка не держит: меняй форму
   ([wording.md](wording.md)), а не досыпай слов.

Микротест проверяет формулировку и не заменяет ни кейсы фазы 2, ни сценарии давления уровня 4.

### Фаза 2 — кейсы

Формула: один и тот же промпт, свежая сессия, **со скилом** и **без** (выключить через
`skillOverrides: {"<skill>": "off"}`). Сравнить результаты.

Если разницы нет — скил не нужен либо не читается; не «докручивай формулировки», а сначала
пойми, чем именно отличается желаемый вывод от базового.

**Начинай с 2–3 кейсов**, не с двадцати. Кейс = промпт + ожидаемый вывод + при нужде входные файлы;
хранится в `evals/evals.json` внутри каталога скила. Каждый кейс гоняется дважды: со скилом и без.

Что фиксировать по каждому кейсу: промпт, входные файлы, ожидаемое поведение, фактический
вывод, вердикт с **конкретным доказательством** (сомнение трактуем как FAIL, а не «ну вроде ок»),
потраченные токены и время. Скил, который улучшает результат на 5% и жрёт 3000 токенов
в каждой сессии, — чистый минус.

Разбор результатов:
- ассерт проходит и со скилом, и без — выкинуть, он ничего не измеряет;
- падает в обоих конфигурациях — разбираться, скил тут ни при чём;
- проходит со скилом и падает без — это и есть польза скила, беречь;
- большой разброс между прогонами — инструкция сформулирована рыхло, ужесточить.

### skill-creator: та же петля, автоматом

```
/plugin marketplace add anthropics/claude-plugins-official
/plugin install skill-creator@claude-plugins-official
/reload-plugins
```

Затем: «evaluate my <skill> skill with skill-creator». Плагин ведёт:
- `evals/evals.json` в каталоге скила — промпты, входные файлы, ожидания;
- изолированный сабагент на каждый кейс + учёт токенов и времени;
- `grading.json` — вердикт по каждому ассерту с доказательством;
- `benchmark.json` — pass rate / время / токены со скилом и без;
- слепое A/B двух версий скила перед коммитом правки;
- тюнинг описания по сгенерированным should/should-not-trigger промптам;
- HTML-отчёт с качественными заметками, которые читает следующая итерация.

Формат eval-файлов и полный цикл: https://agentskills.io/skill-creation/evaluating-skills

## Уровень 4 — скилы-дисциплины (когда скил должен запрещать)

Для скилов, которые заставляют соблюдать правило (а не учат приёму), обычный кейс не годится:
модель нарушает правило не от незнания, а под давлением. Тест — сценарий с 3+ давлениями
одновременно: дедлайн, уже вложенные усилия, авторитет («тимлид сказал»), усталость в конце
длинной задачи.

Цикл: прогнать сценарий **без** скила и дословно записать рационализации → написать скил,
адресующий именно их → прогнать снова → новая рационализация → закрыть явным контром → повтор.

Собранные отмазки идут в таблицу «Отмазка | Реальность» внутри скила. Это дословный текст
из базлайна, а не выдуманные заранее — выдуманные не совпадают с тем, что модель говорит себе.

## Что чем чинить

| Симптом | Причина | Лечение |
| --- | --- | --- |
| Скил не появляется в `/skills` | битый YAML, не тот путь, новый каталог без рестарта | `validate_skill.py`, `--debug` |
| Виден, но не срабатывает сам | в описании нет слов пользователя | переписать `description`, добавить `when_to_use` |
| Срабатывает не там | описание слишком широкое | сузить условие или `disable-model-invocation: true` |
| Описание обрезано в листинге | переполнен бюджет листинга | короче описание, `"name-only"` для второстепенных, поднять `skillListingBudgetFraction` |
| Сработал, но модель проигнорировала инструкции | тело написано как справка, а не как правила | переписать императивами, усилить формулировки, при необходимости — хук |
| Перестал влиять после нескольких ходов | автокомпакт вытеснил содержимое | вызвать заново; сократить тело |
| Форк-скил вернул пустоту | в теле гайдлайны без задачи | добавить явную задачу или убрать `context: fork` |
| Вызов скила падает целиком | инъекция `` !`cmd` `` вернула ≠0 или упёрлась в права | `|| true`, грант в `allowed-tools` |
